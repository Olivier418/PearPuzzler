# Codebase map

Import layering (no cycles): `constants` <- `classes.kernel` <- `classes` <- `serialization` <- `solving` <- `benchmark` <- `plotting`. `classes` never imports `serialization`; anything needing both lives in `solving.py`/`serialization/`. `classes/kernel.py` is a leaf below the rest of `classes`: it imports only numpy and numba and knows nothing about Setup/State/Puzzle.

Core model (`classes/`, layered bottom-up):
- `lattice.py` — `Lattice`: geometry of a board/block's axes (orthogonal vs. offset, e.g. triangular/pyramid). Derives gram2 / `unit_vectors` (every direction of unit length, used by `Setup._valid_orientations` and by the kernel's cell-adjacency table). Leaf, no deps.
- `blocks.py` — `Block` (shape + color/letter + its own Lattice), `BlockCollection` (UserDict, int idx -> Block, unique letters).
- `boards.py` — `Board` (cells: bool ndarray + Lattice), `RegularBoard`, `PyramidBoard(width, depth)` subclasses.
- `setup.py` — `Setup`: board + blocks + **all valid placements** (expensive, computed once, shared by reference across every Puzzle/Book built on it). `placement_cells[block_idx]` = compact cell-index array per valid orientation/position. Compact indexing: grids only cover the board's real cells; `to_full_grid(grid)` / `to_compact_grid(full)` convert to/from the full board-shaped array (used at the rendering / disk boundaries). `render(grid, header=None, leftover_idcs=None)` is a thin facade delegating to `rendering.py`. Two lazy `cached_property` tables: `cell_coords` (compact index -> board position) and `kernel_tables` = `(kernel.Tables, block_ids)`, built once per Setup and shared by every Solver on it — a book is 72 puzzles on one Setup, so caching it here rather than per puzzle is worth ~2x on a book solve. The search's *mutable* state (`kernel.Workspace`) deliberately does NOT live here. `warmup()` builds `kernel_tables` and loads the compiled kernel (`kernel.warmup`, once per process); `solving.timed_solve` and `benchmark` call it before their clocks start so numba's ~0.35 s cache load (seconds on a recompile) isn't billed to the first puzzle. `rows_to_grids(rows)` turns solution rows (see `Solver.solve_rows`) into full board-shaped int64 grids `(k, *board shape)`, identical to `to_full_grid(state.grid)` for the same solutions; `grids_to_rows(grids)` is its inverse and a validity check (raises unless each block covers exactly the cells of one of its placements -- a placement is matched by its sorted cells as one `ravel_multi_index` key). `row_dtype` (cached): uint16 when every block has < 65,536 placements, the dtype rows are stored in.
- `state.py` — `State`: mutable solve state (grid + chosen_placement_idx, `name` = None) over a shared `Setup`. `place`/`remove` (checked) vs `place_unchecked`/`remove_unchecked` (used by Solver). `nr_filled_cells` property. `.solve(seed, time_limit, max_solutions, **options)` is a plain generator delegating to `Solver`; a named state's solutions are renamed "<name> (solution i)"; it prints nothing (progress printing is `solving.py`'s job). `.solve_rows(...)` is the same without States (see `Solver.solve_rows`). Both *return* (generator return value) whether the search ran to the end, as `Solver.solve` does. `render(show_leftover=True)` (via `_print_header`, overridable) builds header + grid + shape diagrams of any still-unplaced blocks; `__repr__` calls it. `Puzzle(State)`: named, has difficulty, optionally pre-filled from a letter grid (`_initialize_grid`, transposes JSON (depth,width) -> internal (width,depth)); header `"Puzzle {name}"`.
- `puzzlebook.py` — `PuzzleBook(UserDict)` (raises `ValueError` if empty): named collection of Puzzles sharing one Setup. `__repr__` expands every Puzzle with `show_leftover=False`.
- `game.py` — `Game`: top-level container of `books` (name->PuzzleBook), `puzzles` (standalone), `setups` (board_key->Setup). One Game per `games/<GameName>/` folder. `board_key(setup)`: a Setup's key (by identity; raises if it isn't the game's) -- how `save_puzzlebook`/`save_bounds` find the board of books they are handed.
- `source.py` — `Source` (frozen dataclass): game/book/puzzle name triple recording where a Puzzle/Book was loaded from. `relative_dir()` -> `<game>/books/<book>` (book), `<game>/puzzles/<puzzle>` (standalone), `<game>/books/<book>/<puzzle>` (one puzzle out of a book). Set by `serialization.loading.load_game`, `None` for hand-built objects.
- `solutions.py` — pure data containers, no solving or I/O: `SolveStats` (puzzle_name, options, seed, duration, elapsed, complete; `options` = free-form solver kwargs besides the seed (`branch`, `order`), kept to tell solver variants apart in benchmarks; only options that leave the solution set alone belong there; `complete` = the run found every solution (True), was cut short by `time_limit`/`max_solutions` (False), or predates the flag (None)), `Solution(puzzle, rows)` (every solution as a row of placement indices -- the solver's own form, ~20x smaller than a grid, so even an empty board's 4.3M solutions fit in ~100 MB; `grids` is a property building full board-shaped grids on each access, `len()` is the solution count, `to_states()` places each row on a fresh State; grids exist only at the edges: solutions.json and printing; **always holds its live `puzzle`** — the one solved, or the one `load_run` found in `games/` — so `puzzle_name`/`setup` are properties and difficulty/filled cells are read off `sol.puzzle`), `SolutionBook` and `SolveStatsBook` (UserDicts keyed by puzzle_name with a book-level `book_name` (+ options/seed for stats); `.name` computed via `_book_name`).
- `solver.py` — `Solver`, the thin Python driver around `kernel.py`. Exhaustive exact cover: `Solver(state).solve(seed=None, time_limit=inf, max_solutions=inf, order=None, branch="both")` yields every solution as a `state.copy()`, stopping early once either limit is hit; `.solve_rows(...)` (same arguments, same order) yields each as a bare row instead -- every block's placement index, pre-placed ones included, in `block_ids` order (= the Setup's block order) -- with no State built: the fast path everything that times or counts uses (`solving.timed_solve`, `benchmark`). Both are thin loops over `_chunks()`, the kernel loop proper, which yields each kernel return's solutions as an array of global-id paths, trimmed to `max_solutions`, and *returns* True if the search ran to the end (kernel DONE), False if a limit cut it short; `solve`/`solve_rows` pass that on as their own generator return value (via the module-level `_each`, since a `for` loop would drop it) -- it becomes `SolveStats.complete`. It owns only what the kernel cannot see: `_start()` turns the State's grid + already-placed blocks into the kernel's `(occ, used)`; `_resolve_rules()` (module level) resolves `branch`/`order` to integer codes; `_emit()` replays a path of global ids through `place_unchecked`, so grid and `chosen_placement_idx` can never disagree. **Laziness**: the kernel is never told `max_solutions`; it gets a solution-buffer cap and a node budget, returns FULL/BUDGET/DONE, and is re-entered with its stack intact. An EMA of nodes/s sizes ~2 ms chunks (`_next_budget`), which is how `time_limit` stays exact to ~2 ms and how the generator stays abandonable mid-tree. The workspace is allocated per kernel entry and never stored, so a reused Solver gives bit-identical output with no reset discipline. **`branch`** picks which kind of item a node branches on (see `kernel.choose_item`): `"both"` (default, the scarcer of the two), `"cell"`, `"block"` — `"block"` is a baseline only, hopeless on an open board. **`order`** ranks a node's candidates; because `kernel.rank` keys off a *placement* and never learns which kind of item was branched on, it applies uniformly to all three `branch` modes. `True`/`"counts"`, `"pockets"`, `"fanout"`; `None` = on iff a limit is set. Seeded with `order=False` sorts by the drawn priority alone, since the branch argmin leaves nothing for a seed to perturb. `SOLVER_WALKTHROUGH.md` is a read-alongside guide to both files; `SOLVER_NOTES.md` has the measurements and what was removed (symmetry, partitioning) and why.
- `kernel.py` — the search itself, compiled by numba; no `classes` imports. A cell is a bit: occupancy is `occ`, `NW = ceil(n_cells/64)` uint64 words, and `pmask[gid]` is the same for a placement, so the conflict test is one AND per word. `nw` is read from `occ.shape[0]` at runtime and looped over, so there is **no cell-count ceiling and no separate path for big boards** — 55 cells and IQquub's 64 both give NW 1; a 200-cell board gives NW 4 and works. `Tables` (per Setup, via `Setup.kernel_tables`, ~70 KB): `pmask`, `pblock`, `pcells`, `psize`, CSR `cell_start`/`cell_pl`, `block_start`, `full`, `neigh`, `fan` = `max(cell degree, block run)` so both kinds of candidate list fit one buffer. `Workspace` = one run's mutable state, allocated per entry. `kernel()` is an **iterative explicit-stack DFS** — numba recursion segfaults, and a stack is what makes the run resumable; every `return` happens with the loop invariant intact, so re-entry is just "run the loop again". `occ == full` is the only termination test: `Setup._validate_area` guarantees the blocks' total area equals the board's, so covering every cell implies placing every block — and the converse, which is what makes `branch="block"` terminate. A placement is its own undo (`^=`). `choose_item` returns `(kind, index)` — kind 0 a cell, 1 a block position — and is what a node costs, not the conflict test; `_count_cell`/`_count_block` cap their scans at the best-so-far count, which is what makes MRV affordable. **Debugging: `NUMBA_DISABLE_JIT=1` runs this exact source as plain Python** (~1300x slower, pdb works) — that is why there is one implementation and no NumPy reference. It constrains the source: index the `BIT` table instead of shifting (numpy 2 promotes `uint64 << int` to float64) and write every literal `np.uint64(...)`. All helpers are module-level — a closure cell would be hashed into numba's `cache=True` key and `benchmark.py`'s trial subprocesses would recompile. `warmup(t)` (idempotent, module flag) compiles/loads once: `benchmark.py` calls it in the parent so trial subprocesses don't race, and in each worker before its "ready" handshake.
- `rendering.py` — terminal display: `grid_lines`, `block_shape_lines`, `legend_lines`, `render(board, blocks, grid, header=None, leftover_idcs=None)`. Plain `Board`/`BlockCollection`/grid args, no `Setup` dependency.
- `_utils.py` — `_assert_unique`, `_shared` (dedup/consistency helpers).
- `__init__.py` — the public re-export surface; import from here, not submodules, in new code.

Serialization (`serialization/`; imports `classes`):
- `loading.py`: `load_blocks`/`load_boards`, `load_setups(game_dir)` ({board_key: Setup}), `load_book(game_dir, book_name, setups)`, `load_standalone_puzzles(game_dir, setups)`, `load_game(dir)` (auto-discovers `books/*.json` + `puzzles/*.json` via those two, builds a full `Game`); every loaded book/puzzle gets its `Source`. `save_puzzlebook(book, game, games_root=GAMES_DIR)` is the inverse for a book made in memory (e.g. `compute_puzzle_bounds`): writes `games/<game>/books/<name>.json` (never overwrites), sets the Sources, adds it to `game.books` — a run can only be saved for puzzles that live in `games/`. Names are never read from a JSON `"name"` field except for puzzles inside a book file: `Game.name` = folder name, `PuzzleBook.name`/standalone `Puzzle.name` = file stem. A board's optional `"cells"` is row strings (`"X"` = cell).
- `puzzles_io.py`: the book-file format (`{"board", "puzzles": [{"name", "difficulty", "grid"}]}`, or a bare list for board "main"), read and written: `read_book_file`, `puzzle_from_entry`, `load_puzzles(file, setups)`, `write_puzzles(puzzles, board_key, file)`.
- `jsonio.py`: leaf letter-grid helpers. A grid is one string per row (`"BBB        "`), a pyramid a list of such layers; `" "` = empty/off-board. `parse_letter_grid`, `letter_grid_to_rows` (from internal (width, depth[, height])), `block_grids_to_rows(grids, blocks)`/`rows_to_block_grids(entries, blocks, shape)` (a batch of full grids of block indices `(k, *shape)` <-> letter-row entries via the blocks' letters, vectorised through one byte string and a lookup table -- seconds for millions of grids; the reader raises on a wrong-sized entry or an unknown letter), `dump_json(obj, path)` (indent 2, list of strings one row per line).
- `paths.py`: leaf; where runs live and how to read names back from a path: `next_free_idx_dir(base, prefix="result")`, `next_run_dir(source, root, prefix="result")` (raises for a source-less puzzle/book, pointing at `save_puzzlebook`; `benchmark` prefix for benchmarks), `game_book_from_run_dir`, `puzzle_name_from_run_dir` (the folder below `books/<book>/` or `puzzles/`; both anchor on the nearest `books`/`puzzles` component, so a benchmark's config folders and `stats<seed>.json` files below are fine, and raise for a path outside the layout).
- `solutions_io.py` / `stats_io.py`: `write_solutions`/`load_solutionbook(file, puzzles, flat_name, book_name)`, `write_solve_stats`/`load_solve_stats_book(file, flat_name, book_name)`, `single_entry`. Grids are letter rows (the format a person can read; unchanged by rows-in-memory): `write_solutions` turns a Solution's rows into grids `_CHUNK` (65,536) at a time, `load_solutionbook` reads every grid back into rows via `Setup.grids_to_rows`, so every loaded solution is checked to be one. `flat=True` (one puzzle; name from the path) writes just the grids / duration+complete+elapsed, `flat=False` (whole book) per-puzzle `{"puzzle_name", ...}` entries. stats.json keeps an object wrapper (`options`, `seed`); `complete` is per puzzle and loads as None from a file that predates it; old-format runs (top-level solver flags) are not supported.
- `runs.py`: `save_run(solution_book, stats_book, folder, flat=True)` / `load_run(folder, games_root=GAMES_DIR) -> (PuzzleBook, SolutionBook | None, SolveStatsBook | None)` — a loaded run is three parallel books keyed by the same puzzle names. Either result half may be None: a run folder is `solutions.json` and/or `stats.json` (a missing file loads as None; raises if both are missing) — no puzzles, since `games/` is fixed (existing puzzles never change; `save_puzzlebook` only adds books), so a reference to it can't go stale: its path (any root, ending in the `Source.relative_dir()` layout) names game/book/puzzle, and the Puzzles are always loaded from that game under `games_root` (`load_book`/`load_standalone_puzzles` on `_game_setups`, lru-cached per game dir per process; ~0.05 s a game), whichever halves exist. The PuzzleBook holds only the puzzles the run covers, named after the book (or the standalone puzzle). There is deliberately no `game=` shortcut: a run only ever refers to puzzles in `games/`; tests use `games_root` on a copied game. `load_puzzle_run(folder, puzzle) -> (Solution | None, SolveStats | None)` loads a single-puzzle run straight onto a Puzzle already in hand (raises if the path names another puzzle). `latest_complete_run(puzzle, root=SOLUTION_DIR) -> Path | None`: the newest `result_<idx>` of `puzzle` holding solutions and stats that say `complete`.
- `bounds_io.py`: a board's bounds folder, `bounds_dir(game_name, board_key, root=BOUNDS_DIR)` -> `<root>/<game>/<board_key>/`, holding the two bound books: `lower_puzzles.json`/`upper_puzzles.json` (book-file format) and `lower_stats.json`/`upper_stats.json` (`flat=False`, every puzzle's, the empty board's included -- self-contained, so deleting runs in `solutions/` never breaks them). `save_bounds(game, lower, upper, root=BOUNDS_DIR) -> folder` (the board is the books' Setup, via `game.board_key`; overwrites) / `load_bounds(game, board_key, root=BOUNDS_DIR) -> Bounds` (`Bounds` = `(lower, upper)`, each a `(PuzzleBook, SolveStatsBook)`, the books named `LOWER_BOUND_BOOK`/`UPPER_BOUND_BOOK`; raises `FileNotFoundError` unless all four files exist). Both are explicit: nothing computes bounds as a side effect of loading, or loads them as a side effect of computing. No staleness check: letter grids describe themselves and `games/` is fixed, the same assumption `solutions/` makes.
- game/book/puzzle names are never written into JSON (except `puzzle_name` in a `flat=False` file); they follow from the folder. On-disk layout: `games/<Game>/{blocks.json, boards.json, books/*.json, puzzles/*.json}`; solutions mirror it under `solutions/<Game>/<books|puzzles>/<name>/[<puzzle_name>/]result_<idx>/{solutions.json, stats.json}`; benchmarks under `benchmarks/<Game>/<books|puzzles>/<name>/[<puzzle_name>/]benchmark_<idx>/<config-label>/stats<seed>.json` (one flat stats file per trial; no solutions); each board's solution bounds under `bounds/<Game>/<board_key>/{lower_puzzles.json, lower_stats.json, upper_puzzles.json, upper_stats.json}` (the empty board's solutions they come from are an ordinary run of `empty_<board_key>` in `solutions/`). `solutions/`, `benchmarks/` and `bounds/` are git-ignored.

Running (`solving.py`, `benchmark.py` at the repo root):
- `solving.py` (saves via `serialization.save_run`): `timed_solve(puzzle, seed, verbose, time_limit, max_solutions, keep_rows=True, progress=False, **options) -> (rows | None, SolveStats)` is the one timing path (solve_puzzle and puzzle_bounds use it, so their times compare): `setup.warmup()` off the clock, then `puzzle.solve_rows` driven by hand (to catch its return value, the `complete` flag) with one elapsed stamp per solution and the `verbose` printing on it (at `SHOW_SOLUTIONS` a State is built from the row to print); rows gather in a doubling numpy buffer (`_RowBuffer`, `setup.row_dtype`), not a list, since an empty board can have millions. `empty_puzzle(game, board_key)`: the game's standalone `empty_<board_key>` puzzle (raises if missing). An empty board's solutions are just an ordinary run in `solutions/` (IQpuzzlerPRO main: 4,331,140 solutions, ~500 MB of JSON, ~40 s to read or write): `solve_puzzle(empty_puzzle(...), save_solutions=True, save_stats=True)` once, then `load_puzzle_run(latest_complete_run(puzzle), puzzle)`. `solve_puzzle(puzzle, seed, verbose, save_solutions, save_stats, path, solutions_root, time_limit, max_solutions, progress=False, **options) -> (Solution, SolveStats)` and `solve_puzzlebook(book, ...) -> (SolutionBook, SolveStatsBook)` (one combined `flat=False` save). Solves and times (`timed_solve`), wraps the rows in a Solution, packages (`single_run_books`) and, only with `save_solutions` and/or `save_stats` (opt-in, independent: the grids are the bulk of a save and the stats are useful without them), saves that half under `solutions/` mirroring the `Source` (or to `path=`; `path` alone saves nothing). `time_limit`/`max_solutions` are deliberately not part of `options` (never recorded or treated as a benchmark config): they change which solutions come back, not how they are found. `verbose` is a `Verbosity` IntEnum (cumulative): `SILENT` 0; `SUMMARY` 1 "Found 21 solutions to puzzle x in 1.23s"; `EACH_SOLUTION` 2 also "Found 3rd solution to puzzle x in 0.42s" per solution; `SHOW_SOLUTIONS` 3 prints each solved puzzle instead of that line (its header already names puzzle + solution number). The summary line ends every level >= 1 (at level 3 it omits "to puzzle x" when a puzzle was rendered above it).
- `benchmark.py`: `run_benchmark(...) -> ({ConfigKey: [SolveStats]}, folder)`/`load_benchmark(folder)` (same dict; no `game`, since no Puzzles are needed), `config_key`/`config_label` (a config = dict of solver keyword options; `DEFAULT_CONFIGS` = a tuple of four `order` configs (`counts`, `pockets`, `fanout`, `False`)). Trials run in a subprocess with a wall-clock cap `T`: the parent owns the authoritative deadline and kills the worker, which also gets `time_limit=T`. The worker solves on `solve_rows`, starts its clock when it sends "ready" (when the parent starts T), stamps each solution itself and sends the stamps in batches at most every `_BATCH_SECONDS` (10 ms; one pipe message per solution cost ~20% throughput), never the solutions, then `("done", (duration, complete))`; the parent waits up to T + `_GRACE_SECONDS` for that, keeps stamps <= T, caps the duration at T and builds the trial's `SolveStats` (complete only if the search ended within T). Only stats are saved. Takes a `Puzzle` that lives in `games/` (has a `source`).

Plotting (`plotting/`): `plot_puzzle_stats.py`: `plot_puzzle_stats(puzzles, stats, x=None, y=None, z=None, title=None, ax=None)` is the one general one-dot-per-puzzle scatter (one dot per entry of `stats`; `puzzles` is any name -> Puzzle mapping covering them, e.g. `load_run`'s PuzzleBook or the book that was solved -- `solved_puzzles` does the lookup and raises `ValueError` for a missing name; no plot takes solutions, since none reads a grid), colored by difficulty (the game's tiers from `DIFFICULTY_COLORS`, the bounds' tags from `BOUND_COLORS`); `z` makes it 3D (log axes become log10 with 10^k tick labels, since 3D can't log-scale). Axes are named `Metric`s from `METRICS` (`nr_filled_cells` (default x), `nr_solutions`, `time_to_first_solution`, `time_to_last_solution`, `solve_time`; `nr_solutions` is `len(stats.elapsed)`), or a custom `Metric(label, value(puzzle, stats), log)`. Puzzles with an undefined value (nan) or a non-positive one on a log axis are dropped. Difficulty/nr_filled_cells are read off the puzzle; puzzles on the same point (values + color) are consolidated into one dot labeled with all their names; an existing `ax` is an overlay: it remembers its metrics (`ax._puzzle_stats_metrics`), so `x`/`y`/`z` are inherited (naming a different one raises), and its legend is extended, not rebuilt. `plot_solve_timeline(puzzles, stats, ax=None)` is deliberately standalone: it draws one mark per *solution* rather than one dot per puzzle. `plot_bounds.py`: `plot_bounds(lower_puzzles, lower_stats, upper_puzzles, upper_stats, title=None, ax=None)` draws `compute_puzzle_bounds`' result on filled cells vs. number of solutions (log): fixed axis limits (autoscaling off, so overlays can't rescale), `OUT_OF_BOUNDS_COLOR` shading below the lower and above the upper bound, a dashed black line along each with a small unnamed black dot (a line marker, smaller than `plot_puzzle_stats`' dots) on each of the bounds' own puzzles; the axes are labelled, styled and given `_puzzle_stats_metrics` via `plot_puzzle_stats.format_axes` (shared with `plot_puzzle_stats`) exactly as `plot_puzzle_stats` would; returns the ax, onto which `plot_puzzle_stats(book_puzzles, book_stats, ax=ax)` overlays a real book of the same board. `plot_benchmark.py`: `plot_benchmark(trials, show_trendline=True)` (`{ConfigKey: [SolveStats]}`, as `run_benchmark`/`load_benchmark` return) draws each trial's cumulative-solutions step curve (anchored at (0,0)) plus the per-config average on a 500-point grid, colored from `constants.CONFIG_PALETTE`; Trendline rate = `_poisson_rate`, the homogeneous-Poisson MLE (total solutions / total observed time, pooled over trials).

`placements.py` (root): `placement_counts(game) -> {board_key: {block_idx: n placements}}` and `print_placement_table(game)` (rows = pieces drawn via `rendering.block_shape_lines`, columns = boards; needs `game.setups`).

`puzzle_bounds.py` (root): `compute_puzzle_bounds(empty_solution, empty_stats, verbose=True) -> Bounds` = `((lower_puzzles, lower_stats), (upper_puzzles, upper_stats))`, pure: no files read or written, always computes; the input is a complete solve of an empty puzzle (raises if the puzzle isn't empty, the stats aren't its, or `complete` isn't True), whose Solution carries the puzzle and hence the Setup/board. Keep the result with `save_bounds`, read it back with `load_bounds` -- the bounds on the number of solutions: for every attainable filled-cell count from 0 (the empty board, included) to one block short of full, a puzzle with the exact fewest solutions (lower bound, tagged `HARDEST_DIFFICULTY`) and one with the exact most (upper bound, `EASIEST_DIFFICULTY`), one example per count even where the bound is 1, named 1, 2, 3, ... by increasing filled count. Books `LOWER_BOUND_BOOK`/`UPPER_BOUND_BOOK` (`"lower_bound"`/`"upper_bound"`, the same on every board); no SolutionBooks. Loading them back takes IQpuzzler main 0.4 s, IQpuzzlerPRO main ~4 s (puzzle 1's stats hold 4.3M stamps). Puzzle 1's SolveStats are `empty_stats`. A realization's solutions are the rows placing its blocks its way, so `bound_counts(table, n_placements, sizes)` (pure, public for tests) groups the rows per block subset -- `_Grouping.dfs` grows a subset by one higher column at a time, refining the parent's group ids with `np.unique` (no solver calls). A singleton group settles every superset's lower bound at 1 (`settle`, realized from its row); once that holds below a node only the upper bound is left, so only rows in groups larger than every reachable filled count's best upper bound are passed on (exact: child groups never outgrow their parent's) -- ~8x faster than grouping every subset. `_bound_puzzles` builds a book from a bound; `_time_bound_book` re-solves its non-empty puzzles with `timed_solve` for their SolveStats, each count checked against the grouping's.

`main.py` is a scratch file of mostly commented-out usage examples, not a real entrypoint. `main.ipynb` is a demo notebook.

`constants.py`: grid sentinels (EMPTY/OUTSIDE_BOARD/UNPLACED), `SOLUTION_DIR`/`BENCHMARK_DIR`/`GAMES_DIR`/`BOUNDS_DIR` (Paths; `BOUNDS_DIR` holds only the bound books), the bounds' difficulty tags (`HARDEST_DIFFICULTY` = "hardest" for the lower book, `EASIEST_DIFFICULTY` = "easiest" for the upper) and the bound books' names (`LOWER_BOUND_BOOK`/`UPPER_BOUND_BOOK`), color tables used only in plotting (`BOUND_COLORS` colors those two tags, `OUT_OF_BOUNDS_COLOR` is `plot_bounds`' shading).

Testing (`tests/`, stdlib `unittest`; run the whole suite by running `run_tests.py` in the repo root, ~6 s; nothing is read from or written to `solutions/`/`benchmarks/`/`bounds/`): `tests/data/<Game>/<book>.json` -- hand-checked solutions used as a fixture (`{puzzle name: [solution, ...]}`, a solution being a list of layers (1 on main/alt boards, 5 on a pyramid) of row strings, `" "` = off-board). IQpuzzler holds one sampled puzzle per difficulty per book; IQpuzzlerPRO holds every puzzle, verified against the solution booklet. Loaded by `_helpers.load_known_solutions`. `test_solver.py` -- known solutions must be valid and among the solver's; every PRO puzzle's booklet solution must be found and every PRO puzzle must have exactly one solution (`pyramid_puzzles/120` is skipped there and pinned as an `expectedFailure`: the real game's claim doesn't hold, 5 solutions); an unsolvable hand-built puzzle has no solution; seeds give identical solution sets; the first 25 solutions of the empty boards are valid and distinct; time/count limits; `solve_rows` + `rows_to_grids` give exactly `solve()`'s solutions in order (pre-placed columns included) and `max_solutions` stays exact on it. Known solutions are built as `Solution(puzzle, rows)` from the literal puzzles' placements. `test_branching.py` -- `branch` (`cell`/`block`/`both`) and `order` (forced on and off) change the route, never the destination: identical solution sets on a spread of book puzzles and on the unsolvable fixture, with `branch="cell"` as the baseline the rest are checked against; solutions stay valid in every mode; `max_solutions` stays exact in every mode; unknown `branch`/`order` names raise. `branch="block"` is pathologically slow on an open board (no solution to `empty_main` in 30 s), so `OPEN_MODES` leaves it out of the two tests that start from one. The 12 pentominoes on 3x20 check the total (8) against a published number; 4x15/5x12/6x10 are the same check by hand, too slow for the suite. `test_data.py` -- puzzle-file sanity (blocks-fill-board is enforced by `Setup._validate_area` at load time, not tested separately). No tests for terminal output formatting. `test_serialization.py` -- letter-grid helpers and run-folder round trips (temp folder only): one puzzle (the loaded PuzzleBook holds just it), a whole book, and a new book given a home with `save_puzzlebook` (into a copied game under a temp `games_root`) before its run can be saved; saving only one half (`save_solutions`/`save_stats`) and neither; `load_benchmark` grouping hand-written `stats<seed>.json` files by config in numeric seed order; `complete` (a `max_solutions`-limited run saved False, a full one True; `latest_complete_run` skips a newer cut-short run; `load_puzzle_run` gives back the same rows and stats; a stats file without the flag loads None); the bound books round-trip through `save_bounds`/`load_bounds`, which raises `FileNotFoundError` while a file is missing. `test_bounds.py` -- `bound_counts` against brute force (every subset grouped from scratch) on random tables, each reported realization really having its count; the whole bounds on a "Pentominoes" game written to a temp games root (`write_pentomino_game`: the 12 pentominoes on 3x20, 8 solutions, with its `empty_3x20` puzzle, solved in memory): book names and tags, puzzle 1's stats being the empty solve's, every puzzle's stats count equals a fresh solve, lower <= upper, a cut-short empty solve rejected, and `plot_bounds` (dashed lines on the bounds, dots as the lines' markers, two shadings and no names, log y, an overlay inherits the axes and keeps the limits). `test_plotting.py` -- smoke tests on the Agg backend: `plot_puzzle_stats` (2D and 3D) and `plot_solve_timeline` take (puzzles, stats), plot `len(stats.elapsed)` as the solution count, and raise when `puzzles` misses a name in `stats`. `_helpers.assert_valid_solution` is the shared validity check.
